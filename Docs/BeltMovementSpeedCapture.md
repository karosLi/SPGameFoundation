# Belt movement speed comparison

`BwMovementSpeedCaptureTests.FullHorizontalInputAndHeldAttackUseActualMovement` is an isolated, opt-in graphics PlayMode fixture. Set `SPF_WEAPON_GAMEPLAY_SEQUENCE=1` and run both parameterized cases on native Unity. It writes four separate `Artifacts/Screenshots/WeaponMotion/belt-movement-{full-input|held-attack}-{gpu|fallback}` directories and leaves the existing eight motion recordings and their input schedules unchanged.

The fixture explicitly selects the approved `SmoothAttackV1` policy through `BwGameBootstrap.CreateWeaponBelt(playerMobility: BwBeltPlayerMobility.SmoothAttackV1)`. Both modes use the same blade, camera, 640×360 target and full horizontal `(1,0)` input through the public `InputRouter.Scripted` source. Only held attack differs. Each records 50 actual camera-target readbacks at a target 30 Hz, with the automatic session clock and normal 1× gameplay/presentation updates. The public spawner places the hero at `(-5,0)` and an ordinary stationary variant-0 target at `(-8,2)` once before acquisition. No per-frame position, velocity, pose, damage or tick injection is used. The target keeps the normal fighting flow alive without approaching or blocking the route.

Every acquired frame is retained as a lossless RGBA PNG; `capture.json`, actual `acquisition.csv` timestamps and `acquisition.ffconcat` come from `BufferedFrameCapture`. Image encoding and trace serialization happen after acquisition. Review the concat at normal 1× speed using its measured durations; the acquisition target is not a claim of exact 30 FPS or a device frame-pacing benchmark. Each sequence reserves 46,080,000 raw bytes; modes are buffered sequentially.

`movement.csv` records actual authoritative ground/previous-ground coordinates, last-tick and between-acquisition deltas, source and router input, tick/simulation time, fighter state/action, weapon stage/timeline/pulse, actual velocity, camera settings, `BwRules.PlayerSpeed`, selected mobility policy and the public windup/active/recovery movement scales. `movement.txt` separately counts phase-attributed windup, active, recovery and unattributed Begin/restart boundary observations. These are readback samples, not exhaustive tick occupancy; automatic updates may advance several ticks between observations. State annotations can be newer than the preceding camera render.

Movement executes before the weapon timeline advances. Exact phase attribution therefore uses the retained authoritative `ActionTimeline.PreviousTick`, not the post-step view stage. Its scale is compared against the actual **single latest tick** displacement `Ground - BwBeltKeys.PreviousGround`, divided by the session tick duration and `PlayerSpeed`. Between-acquisition displacement and its elapsed tick count are recorded separately: an interval may cross multiple phases, so it receives no single-phase ratio assertion. `NextTickIndex - 1` identifies the latest completed simulation tick.

`Begin()` replaces the retained previous timeline tick with `-1`, both on initial admission and held-action restart. These boundary samples remain in the evidence and must keep moving, but their pre-move stage is marked unavailable rather than inferred. The initial admission tick runs at normal speed. Subsequent attributable windup/active/recovery movement uses the public scales `0.75/0.70/0.80` of normal `3.2`, respectively. Native assertions require positive movement in every sampled completed movement tick and every advancing acquisition interval, plus actual coverage and measured ratios for each of the three phases. They also require normal Walk/rate coverage, positive source/router input, real clock/pulse progress, and reject damage, lane drift, wall clamping, nearby obstruction and camera changes. Evidence is written before these semantic assertions, so a failed run retains its measurements.

Historical context: the earlier legacy runtime admitted movement only in Idle/Walk before applying its `.22` expression. A focused 100-tick probe found normal displacement `5.3333297` versus only `0.053333282` while holding blade, with 99 stationary ticks. This is a legacy diagnostic, not the acceptance target for SmoothAttackV1. The older grounded gait recording also intentionally includes small analog inputs such as `(.27,.18)`; it is a separate low-input scenario, not full-speed traversal.

Validation for this follow-up against mobility commit `ab3201ddcf04ebe65dd4be0b7fa3463c2cb0bb71`: the exact native-only fixture compiled with zero warnings/errors against its harness assemblies, using isolated compile-only shims for Unity's double realtime clock and the already-existing native-only `BufferedFrameCapture` surface. A 100-tick runtime probe measured normal displacement `5.3333297` and smooth held-blade displacement `4.0373325` (mean `2.4223995` units/s), with zero stationary ticks. All 97 non-Begin ticks retained the actual pre-step timeline tick; maximum measured phase-ratio error was `0.000004364`. Native Unity/graphics remain **UNRUN**: neither this probe nor the compile shims validate automatic native cadence, rendering or the shimmed APIs. The ordinary fixture is excluded by `SPF_DOTNET_HARNESS`, so an ordinary harness build cannot check its body. No full harness repeat is required for this PlayMode-only fixture update; the mobility implementation owns its aggregate regression run.

This fixture requires the SmoothAttackV1 implementation, adds no runtime capability and changes no production rule or pose. The integration lead owns native execution and publication.

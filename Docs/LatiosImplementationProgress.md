## 集成与可复现性

1. A1、A2、A3 与实验工程各在独立分支提交；由单一集成分支复核，避免并行覆盖调度、注册和 JobHandle 所有权。
2. 每个代码阶段先跑受影响的反例与逻辑测试。集成后统一执行完整 harness、真实 Unity API 编译、冷组合/旧 fixture 对照；报告精确提交、失败、跳过和未运行项目。
3. 原生 Unity 使用独立运行记录。现有 d7 验收仍单独持有；实验工程必须使用独立 project path 和 Library，不能借原工程的包锁或原生结果证明 Latios 可用。
4. 首阶段不更改根工程的 `Packages/manifest.json`、Editor 版本或保存协议。真实实验的锁文件只有经过 Unity 解析后才记为证据；上游样例锁只可用于依赖分析。
5. 旧的可写 NativeArray 借用等兼容入口必须如实标出检查边界。诊断不能伪装成完整内存安全，也不能引入每次读取自动 Complete。
6. A1 导出属于冷路径；A2 热路径、A3 冷启动分配分别测量。没有实测收益时不声称更快，容量、GC 和物理限值不放宽。

首批集成软件源 `4f70cc2` 的 1,533 项逻辑、双 BCL/API 编译、19 冷组合及 86 项 Python 检查见[集成验证](LatiosSpfExtensionsValidation.md)。阶段的代码完成与原生/设备通过分别记录。

## 已取得的表现证据与仍开放的问题

`fc1c10d` 的四段步态与四段伤害字采集目录已逐文件核对 manifest/hash，分别保留 640 和 360 个源帧。由原始采集时间戳编码的 1× MP4 没有丢帧或插帧；匹配的 `f008f8b` 横屏步态对照使用其完整校验过的历史证据。两次实际采集时长不同，未强行重定时。

逐帧、时间标记转场和接触轨迹检查支持较低的行走抬膝、受测角色的地面支撑，以及普通白字/金色暴击字的区分。该方法不等于实时完整观看的主观自然度验收。横屏密集敌人和血条仍挤占伤害字空间，少量竖屏顶部数字仍会被 HUD 遮挡，保留为表现验收待办；先完成当前 A1–A3 集成，再做局部有界可读性修正。不得改变权威伤害、隐藏失败或打乱 d7 音频收尾。

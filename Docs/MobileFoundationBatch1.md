# 移动端基座加固：第一批

本批基于 `claude/fervent-goldberg-pfkvw4` 的 `f6e122c`。范围是所有现有玩法共用的渲染、帧调控、会话生命周期与触屏输入；不增加新的玩法品类，也不改变模拟 Tick 频率、GC 预算或快照文件格式。

## 1. 小批次精灵的上传负载

`SpriteBatch` 的 DataTexture 路径原先不论一页实际有几个精灵，都对完整页面纹理调用 `Texture2D.Apply`。4096 容量页面是 128 KiB；旧的 `Count × 32` 统计只表示有效实例字节，低估了纹理整页上传。

现在每页复用与已有 prefix submesh 匹配的纹理尺寸。shader、32 字节打包格式、mesh、每页 draw 次数均保持原样：

| 一页实际实例数（容量 4096） | 旧完整纹理 payload | 新完整纹理 payload | 减少 |
| --- | --- | --- | --- |
| 1–256 | 128 KiB | 8 KiB | 93.75% |
| 257–512 | 128 KiB | 16 KiB | 87.5% |
| 513–1024 | 128 KiB | 32 KiB | 75% |
| 1025–2048 | 128 KiB | 64 KiB | 50% |
| 2049–4096 | 128 KiB | 128 KiB | 0% |

这是提交给 Unity API 的实例数据 payload，不是 GPU 总线实测流量，也不是帧率提升百分比。实际驱动传输、功耗与发热需要真机测量。

- 小 → 大 → 小会重用对应纹理，不逐帧重新创建。每个缓存维护自己的尾部清理，避免缩容后残留精灵。
- 去掉首次使用前多余的一次全零 `Apply`。
- `Warmup(count)` 可在加载阶段创建到指定数量所需的 page mesh 与纹理缓存；不改变当前实例数据/数量，不提前上传实例纹理。仍然保留按需分配默认行为。
- 代价：全部尺寸都用过或全部预热后，纹理缓存总存储小于原完整纹理的 2 倍（完整 4096 页为 1.9375 倍，CPU/GPU 纹理副本都要考虑）。非二次幂末页也受这个上限约束。大量大批次或显存紧张的设备应实测权衡。
- `BytesUploaded` 每次 Draw 重置，计完整 RGBA8 纹理 payload，或 GPU 实例缓冲 + indirect arguments；空批次和未变化的 `dirty:false` 为 0。它不含 atlas/mesh 初始化与驱动开销。
- 现有玩法的动态 batch 在 Bind/初始化时调用 `Warmup(Capacity)`，防止战斗中第一次跨越 256→257 等阈值时创建新纹理。固定数量的静态地图仍可在首次绘制时创建。
- 预热最大容量还会提前创建原本按需分配的所有 page mesh；因此「<2 倍」仅约束已分配页面的纹理 payload，不代表整个游戏启动常驻内存或加载峰值小于原来的 2 倍。Survivor 默认不透明/弹幕/特效容量分别为 12,352 / 33,024 / 2,048，需在目标机核查这项零 GC 与启动内存的取舍。
- Survivor 的现有性能报告改用每个 batch 的实际计数；旧报告的 `Count × 32` 不能与新 DataTexture 数值直接比较。

## 2. 帧调控边界

`FrameGovernor` 保留原有滞回与温度/电量策略，修复：

- 空闲低帧率后的唤醒帧不会被误判成设备性能差；重新开始一段连续的活跃帧测量。
- 运行时关闭空闲降帧会恢复当前设备允许的活跃帧率，并清除残留空闲计时。
- 活跃目标帧率或温度上限改变时，重置旧目标下的 EMA/滞回历史，跳过过渡帧；相同目标重复设置不重置历史。
- 忽略 NaN、无穷、负数等无效时长，防止污染后续帧预算。

不宣称已经解决所有自适应画质问题。多个 governor 对全局 `Application.targetFrameRate` 的所有权与退出恢复，需要独立设计和验证；本批不扩大范围。

## 3. 九种现有玩法共用的 Session 生命周期

所有现有 bootstrap 都使用 `SessionHost`，无需复制一套游戏专用恢复代码：

- 禁用 Host、应用进入后台或失去焦点时，先完成在途 Job，再停止调度；独立的末帧 launcher 也一起停。
- disable、background、focus 三种原因全部解除后才能恢复。游戏菜单主动 Pause 与系统中断分别记录，恢复前台不会关闭玩家的暂停。
- 首次恢复的实时帧丢弃后台墙钟时长，不补跑一串追赶 Tick。普通暂停保留玩家已请求但未执行的回合。
- Restart 与快照恢复清除旧时间线的待执行回合和帧统计，防止撤销、读档、重开后执行旧操作。
- `RequestTicks` 饱和到 int.MaxValue，不会溢出为负数；释放后的请求会明确抛出异常。
- 销毁 Host 后不会遗留继续运行的 launcher。

这是运行中断策略，不是自动存档。系统直接杀进程、移动端来电/键盘/通知面板组合仍需要真机覆盖。

## 4. 触屏接入边界

共用触控控件增加单指所有权与中断重置，避免另一个手指释放当前摇杆/按钮，或进入后台后保持移动、跳跃、开火状态。正常短按仍保留 `ConsumePress` 的一次按下沿。

手势取消与普通松手分开：取消不会生成点击、滑动或松手发射；双指操作的最后一根手指也不会意外生成单指完成动作。此处会影响 Sling 的发射与 Puzzle 的交换，因此配套覆盖取消、pinch→单指和重新开始操作。

## 5. 验证记录

测试结果以同机原始源码基线和最终代码回归为准。完整原始输出保存在本地 `Artifacts/`，不把编辑器结果称为手机验证。

- 环境：Unity 2022.3.62f2，Linux x86_64，Burst 1.8.27；PlayMode 为 Mesa llvmpipe OpenGLCore 软件渲染。
- 原始源码 Unity EditMode：245 通过，0 失败，2 个 Explicit 跳过。
- 原始源码 Unity PlayMode：56 通过，0 失败，0 跳过；包含两档渲染、UI 自动化与浸泡。
- 原始源码 .NET harness：245 通过，2 个 Explicit 未执行，完整 61 个程序集工程构建通过（含 Unity 桩和数学库）。
- 最终 Unity EditMode：323 通过，0 失败，2 个 Explicit 跳过；较基线增加 78 项通过。此轮开启图形设备，包含 4 个真实 Unity 上传/像素数据测试。
- 最终 .NET harness：319 通过，0 失败，2 个 Explicit 未执行；62 个程序集工程构建 0 警告/0 错误。4 个依赖真实纹理/图形 API 的新增测试明确不在桩环境运行，因此与 Unity 的 323 项差 4 项。
- 最终 Unity PlayMode：61 通过，0 失败，0 跳过；较基线增加 5 项（4 个会话生命周期用例、1 个跨尺寸像素一致性用例）。原有双渲染层、UI 自动化、浸泡和 GC 断言全部保留且通过。
- 独立静态审查完成；审查发现的前缀首次跨越分配风险已通过生产预热接入修复，并回查无未解决的重要发现。
- 新增跨前缀/第二页的像素测试：4097 与缩回 1 个实例的 GPU/DataTexture 截图逐像素完全一致；尺寸切换、尾部残留与空批次均有断言。
- 本轮 Survivor 渲染压力窗口两档均为 240 帧/0 B 托管分配。自动游玩仍有零星分配：排除既有界面切换邻近帧后，GPU 为 7 帧 ×117 B =819 B、DataTexture 为 2 帧 ×164 B =328 B（每个窗口180帧），均在原有1024 B预算内。含界面切换的窗口总数分别为2693 B与2296 B。来源尚未定位，不能宣称所有玩法已全程0 GC，或把不同跑次的变化归因为本批性能收益。

新增覆盖包括：纹理字节一致性与尾部清理、缓存内存上限、页边界、warmup 稳态零托管分配、上传计数；帧预算/温度变化；会话暂停所有权、回合清理；真实 Unity Update/LateUpdate 的 disable/enable/destroy 流程；触屏多指与取消。

复现入口仍是 `Tools/DotnetHarness/run.sh` 和 `UNITY_EDITOR_PATH=... Tools/ci/local-unity-tests.sh`。受限容器若并行 MSBuild 静默失败，可先运行 `fetch-deps.sh`、`generate.py`，再对生成的 Harness.proj 使用 `dotnet build -m:1 -p:BuildInParallel=false` 与 `dotnet test --no-build -m:1`；这只是执行环境 workaround，不改变测试或产品阈值。

## 6. 下一批优先级

1. Android/iOS Development Player：实测 GLES3、Vulkan/Metal 的纹理传输、GPU 帧时间、缓存内存、发热/电量策略与中断输入；目前只有桌面编辑器证据。
2. 用真机 Profiler GC.Alloc 调用栈追踪 Survivor 的零星 164 B 分配；保留既有 ≤1 KB/稳态窗口预算，不扩大阈值来掩盖来源。
3. 在当前动态 batch 全容量预热保障下，量化每个玩法的加载峰值/常驻内存；据目标机预算收紧 batch 容量或选择分阶段预热，同时保留已验证的零 GC 范围。
4. 完善移动端暂停/恢复与存档持久化策略、内置精简 CJK 字体。根据真实产品需求再扩展新玩法能力。
